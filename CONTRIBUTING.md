# Contributing to Oliver's mTOR Atlas

Thanks for looking. This project is maintained by one curator, and outside eyes are genuinely the most useful thing it gets — the evidence grading has already been improved once by an unsolicited critique from a researcher in the field.

There are four kinds of contribution, in rough order of how much they help.

## 1. Tell us a study is graded wrong

This is the most valuable contribution, because grading is a judgement call and a single curator's judgement is exactly the thing that needs checking.

Open an issue with the label `grading`, and include:

- the study's Atlas ID (the `SID`, e.g. `SAB1994`) or its DOI/PMID,
- the grade it currently has and the grade you think it should have,
- one sentence on why.

Grades are assigned from **study design**, not from quality, importance, or citation count. A mechanistic paper is not "worse" than a trial — it answers a different question and licenses different claims. Disagreements about where a mixed-design paper belongs (human cells plus mouse, say) are the interesting cases and are welcome.

## 2. Tell us a study is missing

Open an issue with the label `study`, and include the DOI or PMID plus one line on what it establishes. Negative results, failed replications, and studies that contradict something already in the corpus are actively wanted and are systematically harder to find than positive results — those are the most useful submissions of all.

The corpus is curated, not exhaustive: not every mTOR paper belongs in it. Selection favours primary discoveries, model-organism longevity and healthspan work, human trials involving mTOR inhibitors, and negative or contradictory findings.

## 3. Report a bug on the site or in the data

Open an issue with the label `bug`. Include the URL, what you saw, and what you expected. Data problems (a wrong year, a mangled author string, a broken DOI link) count as bugs and are quick to fix.

## 4. Contribute code

Pull requests are welcome. Before opening a large one, please open an issue first so we can agree on the approach — some parts of the build have non-obvious constraints.

### Layout

The published site is generated by Python from baked JSON snapshots of the curated data:

- `atlas_data/*.json` — baked data snapshots (studies, entities, gaps, author bios, events). These are generated from the upstream curation database; do not hand-edit them.
- `build_pages.py`, `generate.py` — static page generation.
- `pathway/model.json` — the single source of truth for pathway biology. Never edit it by hand; it is generated by `build_pathway_model.py`.
- `verify_*.py`, `validate_*.py`, `check_tier_palette.py` — the verification suite (see below).

### Running the checks

The project has no unit-test framework; verification is done by a suite of standalone scripts that assert invariants over the generated output. Run them after any change to the generators:

```
python verify_prerender.py        # every static page has real rendered text
python verify_index_html.py       # index.html integrity
python check_tier_palette.py      # evidence-code colours and labels are consistent site-wide
python validate_pathway.py        # pathway model is internally consistent
python validate_claims.py         # curated claims resolve to real studies
python verify_academy.py          # Academy lessons and quizzes are well-formed
python verify_practice.py         # Practice Arena items resolve
```

A change that makes any of these fail should not be merged.

### Conventions

- Keep generated output deterministic — the same inputs must produce byte-identical pages, so that diffs mean something.
- Don't introduce a dependency without saying why in the PR.
- Prose that describes evidence must not overstate it. This project's editorial line is that a mechanistic result is a mechanistic result; if a claim has only mouse data behind it, the text says so.

## Code of conduct

Be straightforward and civil. Criticism of the data, the grading, or the code is welcome and wanted; personal hostility is not.
