# Open mTOR Atlas — Project Handoff

The only mTOR resource that shows not just what a study found, but how strong that evidence actually is.

Live site: https://mtor-atlas.org (GitHub Pages) · Repo: https://github.com/open-mtor-atlas/atlas (branch `main`)

This file is written for a fresh Claude instance (or a new machine) picking up this project with **no prior context**. Read this before touching anything, especially `index.html`.

## 1. What this project is

Petr (working with Oliver, a biology-focused collaborator) is building an AI research assistant over a hand-curated corpus of ~255 mTOR studies. The differentiator versus a generic RAG tool: it doesn't just answer "what do we know" — it also surfaces "what we don't know and why" (knowledge gaps + testable hypotheses), with every claim graded by evidence tier (A = systematic review/meta-analysis, B = human trial, C = animal model, D = mechanistic/in-vitro/review) and cited back to source. Mentorship goal: show this to groups around David Sabatini's lab.

Voice/level for any written or generated content: explain at a level a highly motivated high-schooler interested in mTOR could follow, but with the rigor of a working biomedical scientist. Use primary literature (PubMed / Europe PMC), not secondary summaries.

**Language policy:** every Atlas deliverable (Airtable fields, docs, code, web copy) is in English — this overrides any general instruction to write in Czech. It was an explicit decision by Petr on 2026-07-08.

## 2. Data model — Airtable is the source of truth

Base **"mTOR Studies"**, base ID `appt2U6ObDHUcRlrj`.

- **Studies** (`tblbQIQtzn2vWaV6d`) — ~255 records. Title/DOI/PubMed abstract/Key_Finding/Evidence_Tier/Pyramid_Level, plus AI-extracted fields (`AI_Intervention`, `AI_Target`, `AI_Species`, `AI_Effect`, `AI_Side_Effects`, `AI_Confidence`, `AI_Extracted`), plus Phase-4 license-gate fields (`License`, `Chunkable`).
- **Entities** — knowledge-graph seed (mTORC1/mTORC2/TSC complex/etc.), linked to Studies.
- **Knowledge_Gaps** (`tbloErgZTWR02iSAq`) — H1–H6, gap-finder output: evidence deserts + testable hypotheses.
- **Authors** (`tblmci5ykJTG6sVg2`) — ~488 rows, auto-built by a batch script on 2026-07-07. **Rule: link existing authors to new studies/events; do not create new Author rows outside deliberate additions**, to keep this table's provenance clean.
- **Events** (`tbl142mcSZeCMay7o`) — mTOR/aging conferences (Prague Metabolism & Signaling Symposium 2026, Keystone meetings, ARDD, etc.), linked to Authors as speakers.

`sync_airtable.py` regenerates the `ATLAS_STUDIES`/`ATLAS_GAPS` JS constants inside `index.html` straight from Airtable (read-only PAT via `AIRTABLE_TOKEN` env var — never hardcode it, it isn't in this repo). **Anything added directly to `index.html` without also being added to Airtable will be silently wiped on the next sync** — always write to Airtable first (or in the same pass).

`ATLAS_EVENTS` (Events tab) and the `oq-wrap` "Open Questions" cards are hand-baked, NOT regenerated by `sync_airtable.py` — safe from that particular wipe, but also means they go stale unless someone manually re-syncs them against new studies/gaps.

## 3. The pipeline (phases 0–4)

Documented fully in `docs/Atlas_assessment_and_plan.md` and the packaged skill at `atlas_skill/mtor-atlas-pipeline/SKILL.md` (also exported as an installable `atlas_skill/mtor-atlas-pipeline.skill`).

- **Phase 0 (done):** Airtable → `atlas_data/studies_enriched.jsonl` / `.csv`, PMID/PMCID resolved, free-PMC-fulltext flagged.
- **Phase 1 (done):** local TF-IDF retrieval (`atlas_rag/`) — no external embeddings API, works offline. Swappable interface if a real embedding model becomes available.
- **Phase 2 (done):** LLM structured extraction over all Studies (intervention/target/species/effect/side-effects/confidence), written back to Airtable.
- **Phase 3 (done):** `atlas_gaps/gap_finder.py` — joins the Entities graph against evidence tiers → knowledge gaps + hypotheses (H1–H6 in Airtable + `atlas_gaps/PHASE3_knowledge_gaps.md`).
- **Phase 4 (in progress):** full-text deep search. License gate (`atlas_gaps/license_gate.py`, `licenses.csv`) classifies each study CC-BY / CC-BY-NC / CC-BY-ND / no-open-license. **Split policy (Petr's explicit decision): derived facts (dose/N/effect size) may be extracted from ALL studies with free full text; verbatim text passages may only be stored/served for the ~35 non-ND open-licensed studies** (`Chunkable` checkbox in Airtable). `atlas_fulltext/` holds fetched full texts, chunking (`build_chunk_index.py` → `chunk_index.json`), and the deep-search index the live site loads on demand.

## 4. Web app (`index.html`, ~1.2MB)

Single self-contained vanilla HTML/CSS/JS page. Studies baked into `const ATLAS_STUDIES`, gaps into `const ATLAS_GAPS`, events into `const ATLAS_EVENTS`, author bios into `const AUTHOR_BIOS`. Tab system via `showView()` / `data-tab`. Notable tabs: **Ask Atlas** (client-side TF-IDF RAG + suggested queries + copy-LLM-prompt), **Gaps & Hypotheses** (renders `ATLAS_GAPS`), **Events**, **Authors** (Top-5 authors open a `showAuthorBio()` bio modal with a study-milestone timeline; the full author table still uses the older `filterStudiesByAuthor` filter).

## 5. ⚠️ Critical known issue: silent file truncation in this folder

This project's local folder is OneDrive-synced (`Documents\Claude\Projects\...`), bridged into the sandbox. **Any tool's write to ANY file in this folder — Edit, Write, plain Python `open().write()+fsync()`, even Windows `copy` — can be silently truncated or reverted**, with no error and sometimes with the byte count coincidentally matching the original file. This has broken the live site multiple times (missing closing `</html>`, dropped mid-function) and the breakage was only caught after a manual deploy or a user report of "looks stuck on an old version."

**Rules for any future edit to this repo's files, especially `index.html`:**
1. Avoid the `Edit` tool on files in this folder if at all possible. Prefer building the full new content, writing it, then independently re-verifying.
2. After ANY write, verify from a **fresh, independent** read (new shell call) — don't trust the tool's own success message or a same-call read-back. Check `wc -c`, `tail -c 200` (must end `</html>` for `index.html`), and structurally validate (`node --check` the extracted `<script>`, `json.loads` the `ATLAS_STUDIES`/`ATLAS_GAPS`/`ATLAS_EVENTS` blocks with an expected record count).
3. `verify_index_html.py` encodes these checks; `deploy.bat` now gates on it twice (after backup, after restore) and aborts rather than pushing a broken file.
4. If splicing JSON objects into an array literal, never let the replacement anchor swallow the pre-existing closing brace — insert `, {new...}` as pure addition. Compare `<div>`/`</div>` counts before/after any HTML nesting edit.
5. `.git/index.lock` and ref locks (`main.lock`) are sometimes un-removable from a sandboxed shell — write `.git/refs/heads/main` directly with the target SHA rather than fighting `git update-ref`, and use plumbing commands (`hash-object`, `mktree`, `commit-tree`) to avoid the index lock entirely if needed.

Full incident history and exact fix patterns: see the four project memory files listed in section 8 — read `index-html-large-file-writes.md` in full before doing any large edit to `index.html`.

## 6. Deploying

Run `deploy.bat` (Windows) from the project root — **this is the only supported deploy path**, it replaces older `deploy_*.bat`/`git_*.bat` scripts. It: stamps the "last updated" timestamp, optionally refreshes Airtable data if `AIRTABLE_TOKEN` is set, rebuilds the deep-search chunk index, verifies `index.html` isn't already corrupt, backs it up and re-verifies the backup, syncs to `origin/main`, restores + re-verifies the two deploy files, commits, and pushes. It aborts before commit/push if any verification fails. `deploy.sh` is an older/unix variant — prefer `deploy.bat`.

**Automated (Cowork sandbox) deploys were disabled** after repeated stuck `git` lock failures — deploys are currently run manually by Petr from his own machine.

## 7. Connectors, credentials, and scheduled task — what needs to be reconnected

- **Airtable MCP connector** — used interactively for reads/writes to the base above. This is an account-level Claude connector; it should reconnect automatically when signed into the same Claude account on the new machine (may need a one-time re-approval).
- **PubMed/Europe PMC MCP connector** (`search_articles`, `get_full_text_article`, `get_copyright_status`, etc.) — same account-level connector, used to source/verify every study before it goes in the corpus. Note: `get_copyright_status` has been intermittently returning 500 errors (confirmed 2026-07-09) — the license gate falls back to querying Europe PMC directly per-PMID via `web_fetch` (URL-encode the query, one PMID per call, a few seconds apart to avoid rate limits) when that happens.
- **`AIRTABLE_TOKEN` environment variable** — a read-only Airtable PAT used by the standalone scripts (`sync_airtable.py`, `bake_from_mcp.py`, deploy pipeline). Not stored anywhere in this repo. Must be set again as an env var on whatever machine runs `deploy.bat`/`sync_airtable.py`.
- **`.git/.credentials` inside this project folder contains a live stored Git credential (GitHub push token) — do not include this folder as-is in anything shared outside your own machines.** If zipping this folder to transfer, either delete `.git/.credentials` first and re-authenticate git on the new machine, or make sure the zip only ever goes directly between your own devices.
- **Scheduled task `mtor-atlas-daily-check`** (daily 02:02 local time) — lives outside this project folder, at `C:\Users\petr.barton\Documents\Claude\Scheduled\mtor-atlas-daily-check\` on this machine. It checks for new relevant mTOR studies/symposia, adds them to Airtable, links event speakers to existing Authors, and notifies Petr — it does **not** deploy to the live site (that stays manual). This won't transfer just by zipping the project folder; either copy that Scheduled task folder too, or recreate the scheduled task on the new machine (ask Claude there to set up a daily 2am check with the same description).

## 10. Recommended first steps on the new machine

1. Confirm the Airtable and PubMed connectors are connected (or reconnect them) before running any pipeline step.
2. Re-set `AIRTABLE_TOKEN` if you intend to run `sync_airtable.py` or `deploy.bat`'s optional refresh step.
3. Before editing `index.html`, read section 5 above in full and do a test read/write/verify cycle to confirm this new environment doesn't have the same OneDrive-mount truncation issue (it may be specific to this machine's OneDrive sync, not a universal problem).
4. Decide whether to commit + push the pending local changes (section 9) before or after transfer — if zipping, they'll come along either way since they're just uncommitted files on disk.
5. Recreate or copy over the `mtor-atlas-daily-check` scheduled task if you want the daily automated check to continue.
